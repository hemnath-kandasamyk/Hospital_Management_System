# 🏗️ System Architecture

# Hospital Management System (HMS)

---

# 1. Introduction

The **Hospital Management System (HMS)** follows a **Layered Architecture** that separates the application into independent modules based on their responsibilities. This design improves maintainability, scalability, testability, and code organization while following modern software engineering best practices.

Each layer has a well-defined responsibility and communicates only with adjacent layers, ensuring loose coupling and high cohesion.

---

# 2. Architecture Overview

The Hospital Management System is built using a **4-Layer Architecture**, where each layer performs a specific role within the application.

```text
Presentation Layer
        │
        ▼
Service Layer
        │
        ▼
Data Access Layer
        │
        ▼
Database Layer
```

# 3. Layered Architecture

## 3.1 Presentation Layer

The Presentation Layer is responsible for interacting with users.

It receives requests from users and displays the responses generated by the backend.

### Technologies

* HTML5
* CSS3
* JavaScript
* Flask Routes (Controllers)

### Responsibilities

* User Interface
* Form Validation
* Navigation
* Request Submission
* Display Results
* Error Messages

Example Components

* Login Page
* Dashboard
* Patient Registration
* Doctor Management
* Appointment Booking
* Billing Page

---

## 3.2 Service Layer (Business Logic)

The Service Layer contains the core business logic of the application.

This layer processes user requests, validates data, applies business rules, and coordinates communication between controllers and the database.

### Responsibilities

* Patient Registration Logic
* Appointment Scheduling
* Doctor Availability Validation
* Billing Calculations
* Prescription Processing
* Authentication
* Authorization
* Report Generation

Example Services

* PatientService
* DoctorService
* AppointmentService
* BillingService
* AuthenticationService

---

## 3.3 Data Access Layer (Repository Layer)

The Data Access Layer is responsible for all interactions with the database.

Instead of writing SQL queries throughout the project, this layer provides reusable methods for creating, retrieving, updating, and deleting records.

### Technology

* SQLAlchemy ORM

### Responsibilities

* CRUD Operations
* Database Queries
* Transaction Management
* Data Persistence
* Connection Handling

Example Repository Classes

* PatientRepository
* DoctorRepository
* AppointmentRepository
* BillingRepository

---

## 3.4 Database Layer

The Database Layer stores all persistent application data.

Initially, the project will use **SQLite** for simplicity during development.

In future versions, the system can be migrated to **PostgreSQL** without significant changes to the business logic due to the abstraction provided by SQLAlchemy.

### Development Database

* SQLite

### Production Database

* PostgreSQL

### Stored Information

* Users
* Patients
* Doctors
* Appointments
* Prescriptions
* Medical Records
* Bills
* Departments

    ▼

    │
    ▼

    │

# 12. Architecture Summary

The Hospital Management System is designed using a modular layered architecture that separates the presentation, business logic, data access, and database layers. This approach ensures that the application remains maintainable, scalable, secure, and easy to extend as new features are added.

By following modern software engineering practices and Object-Oriented Programming principles, the project provides a strong foundation for building a production-quality healthcare management application.
